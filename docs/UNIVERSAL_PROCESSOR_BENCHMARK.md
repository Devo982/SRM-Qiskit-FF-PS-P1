# Universal Processor A/B Architecture Benchmark

## 1. Purpose and scope

This document describes the repository's separate Qiskit-based architecture experiment. It compares how one fixed five-logical-qubit workload compiles and behaves under noisy simulation on two synthetic processor configurations.

This experiment is **separate from PS-P1 Quantum-Safe Hybrid Key Exchange**. It does not implement ECDH, ML-KEM, a cryptographic protocol, quantum key distribution, or a quantum implementation of the key exchange. Results are simulator-based and do not establish the performance of real quantum hardware.

The guiding question is:

> For the same logical workload, how do the defined Processor A and Processor B connectivity maps affect compiled circuit cost and noisy-simulation metrics?

The comparison is between the two configurations as specified—not a controlled test of connectivity alone—because Processor A has five physical qubits while Processor B has nine.

## 2. Processor configurations

Both configurations use the same native basis-gate set, noise parameters, transpiler optimization level, transpiler seed, and shot count. Their connectivity and physical-qubit budgets differ.

| Property | Processor A | Processor B |
|---|---|---|
| Physical qubits | 5 | 9 |
| Coupling topology | Linear chain | 3 × 3 grid |
| Undirected coupling edges | (0,1), (1,2), (2,3), (3,4) | (0,1), (1,2), (3,4), (4,5), (6,7), (7,8), (0,3), (1,4), (2,5), (3,6), (4,7), (5,8) |
| Basis gates | `rz`, `sx`, `x`, `cx` | `rz`, `sx`, `x`, `cx` |
| One-qubit depolarizing probability | 0.001 | 0.001 |
| CX depolarizing probability | 0.005 | 0.005 |
| Readout-error probability | 0.01 | 0.01 |
| Transpiler optimization level | 1 | 1 |
| Transpiler seed | 42 | 42 |
| Measurement shots per case | 4096 | 4096 |

The source of truth for these settings is `processors/processor_A.json` and `processors/processor_B.json`.

## 3. Fixed logical workload

The benchmark uses the same five-logical-qubit weighted ZZ stress workload for both processors. It sweeps `reps = 1, 2, 3`, with `theta = 0.37` and `beta = 0.23`.

The weighted ZZ interaction list is:

| Qubits | Weight |
|---|---:|
| (0, 1) | 1.0 |
| (1, 2) | 0.8 |
| (2, 3) | 1.2 |
| (3, 4) | 0.9 |
| (4, 0) | 1.1 |
| (0, 2) | 0.6 |
| (1, 3) | 0.7 |

The workload contains interactions that are not all nearest-neighbour interactions on Processor A's chain. The transpiler must map the logical workload onto each processor's specified coupling constraints. Processor B also has a larger physical-qubit budget, which is an additional difference in this comparison.

The ideal reference is calculated separately from the noisy sampled result. This enables the run to report observable error and distribution fidelity rather than treating the noisy simulation as the reference truth.

## 4. Methodology and reported metrics

For each processor and each repetition count, the pipeline builds the logical circuit, transpiles it for the processor's basis gates and coupling map, simulates the compiled circuit using the configured noise model, and evaluates the resulting metrics.

- **Logical depth:** depth of the uncompiled logical workload.
- **Transpiled depth:** depth after mapping and compilation to the target constraints.
- **Native CX count:** number of `cx` gates in the compiled circuit.
- **Diagnostic SWAP count:** SWAP count from a diagnostic compilation that permits explicit SWAP gates. It is a routing diagnostic, not a claim that the final native-basis circuit contains that number of literal SWAP gates.
- **SWAP-equivalent CX proxy:** an approximate comparison derived from the CX overhead relative to an unconstrained compilation. Treat it as a diagnostic proxy, not an exact physical gate count or a hardware cost model.
- **Noisy observable estimate:** observable value estimated from noisy, finite-shot simulation.
- **Absolute observable error:** absolute difference between the noisy estimate and the ideal reference expectation.
- **Distribution fidelity:** fidelity-style comparison between the sampled noisy output distribution and the ideal reference distribution. It is a classical simulation metric, not a cryptographic or hardware-security metric.

The configured shot count is 4096 per case, and the simulator seed is 42. Finite-shot sampling means the noisy metrics can vary with the random seed, and the reported values should be interpreted in the context of this configured simulation model.

## 5. Recorded comparison

The table below reproduces the comparison table generated by `scripts/analyze_quantum_results.py` in the current benchmark artifacts.

| Reps | Logical depth | A/B transpiled depth | A/B native CX count | A/B diagnostic SWAP count | A/B distribution fidelity | A/B absolute observable error |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 8 | 34 / 30 | 27 / 17 | 5 / 1 | 0.997488 / 0.998163 | 0.184296 / 0.130585 |
| 2 | 16 | 78 / 57 | 62 / 37 | 12 / 3 | 0.943295 / 0.966655 | 1.218163 / 0.909716 |
| 3 | 24 | 116 / 84 | 93 / 57 | 19 / 5 | 0.967119 / 0.979299 | 0.977815 / 0.769416 |

In these recorded runs, Processor B has lower transpiled depth and fewer native CX gates for all three repetition counts. Its measured distribution fidelity is higher and its absolute observable error is lower in all three cases.

The differences in transpiled depth (B minus A) are -4, -21, and -32 for reps 1, 2, and 3. The differences in native CX count are -10, -25, and -36. These results are consistent with the greater routing flexibility of the grid for this workload, but they do **not** isolate topology as the sole cause: the grid also has nine physical qubits, compared with five for the chain.

Distribution fidelity is not strictly monotonic as repetitions increase. Avoid drawing a general scaling law from three repetition counts. These are results for one workload, two specified configurations, one synthetic noise model, and finite-shot simulations—not universal claims about quantum processors.

## 7. Reproduce the experiment

Run these commands from the repository root in a terminal with `uv` installed.

### 7.1 Install the locked development environment

```cmd
uv sync --locked
```

The `dev` dependency group includes the notebook and kernel tooling required for notebook execution and rendering.

### 7.2 Run all six processor/workload cases

```cmd
uv run --locked python scripts/run_quantum_benchmark.py
```

The runner executes Processor A and B for reps 1, 2, and 3. Review the terminal's run ID and completion status, and inspect `results/logs/quantum_run_manifest.json` to confirm that the run status is `PASS` and all six cases completed.

### 7.3 Rebuild comparison tables and figures

```cmd
uv run --locked python scripts/analyze_quantum_results.py
```

The analyzer validates the raw metrics and writes the processed summary, A/B comparison table, and figures listed above. To use a different raw CSV, processor-config directory, or output root, consult:

```cmd
uv run --locked python scripts/analyze_quantum_results.py --help
```

### 7.4 Execute the end-to-end notebook

Register the repository environment as a Jupyter kernel (needed for a fresh checkout):

```cmd
uv run --locked python -m ipykernel install --sys-prefix --name python3 --display-name "Python (SRM-Qiskit-FF-PS-P1)"
```

Then execute the notebook:

```cmd
uv run --locked python -m nbconvert --execute --to notebook --inplace main.ipynb --ExecutePreprocessor.timeout=1200
```

This executes the notebook and saves its outputs into `main.ipynb`. A local Jupyter kernel must be available; the repository environment's `ipykernel` dependency supplies the kernel package.

### 7.5 Run the automated test suite

```cmd
uv run --locked python -W error -m pytest -q
```

A passing test suite checks the implemented behavior; it does not replace inspection of the benchmark manifest, tables, figures, or methodology.

## 8. Limitations and responsible interpretation

1. **Simulation, not real hardware.** The results come from Qiskit transpilation and a configured synthetic noise model. No physical processor was measured.
2. **Unequal physical-qubit budgets.** Processor A has five physical qubits and Processor B has nine. The comparison does not isolate connectivity alone.
3. **Model dependence.** The noise parameters are configured assumptions and do not establish that either topology represents a particular real device.
4. **Finite-shot uncertainty.** The noisy observable and output distribution are estimated from 4096 shots per case; sampling affects the estimates.
5. **Workload dependence.** Only the specified five-qubit weighted ZZ workload and reps 1–3 are represented in the reported table.
6. **Diagnostic metrics are not physical guarantees.** SWAP diagnostics and the SWAP-equivalent CX proxy help compare compilation overhead; they should not be presented as exact runtime, energy, fidelity, or hardware-cost measurements.
7. **No cryptographic claim.** This architecture benchmark does not measure the security, latency, or performance of ECDH, ML-KEM-768, or the PS-P1 hybrid exchange.
